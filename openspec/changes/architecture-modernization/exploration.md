## Exploration: architecture-modernization (5-goal audit vs. shopping-cart baseline)

Baseline: single `:app` module, package-by-layer under `com.pedidosya.kata`, AGP 8.6.1 / Kotlin 2.0.21 / compileSdk 35 / minSdk 24 / targetSdk 35, Compose BOM 2025.05.00, Material3 1.3.2, manual `AppContainer` DI, Room SSoT for cart, Retrofit+kotlinx.serialization for network, MockK+Turbine+kotlinx-coroutines-test for unit tests. Prior change `shopping-cart` completed/archived (Engram `sdd/shopping-cart/design`, `sdd/shopping-cart/proposal`).

Uncommitted local edits (git status): `MainActivity.kt` now wraps `KataNavHost` in a `Scaffold` with a global `TopAppBar` whose back-icon `IconButton` is ALWAYS rendered (hardcoded non-null `onBack` lambda), even on the Cart start destination where `popBackStack()` is a no-op — cosmetic bug, flagged not fixed (out of scope, user left it deliberately uncommitted). `KataNavHost.kt` now accepts an externally-owned `NavHostController` param (default `rememberNavController()`) instead of creating its own — MainActivity creates one `rememberNavController()` and threads it through consistently, so the plumbing itself is correct; only the always-visible back button is the actual defect.

### Goal 1 — Navigation 3 migration
Current: Jetpack Navigation 2 (`androidx.navigation:navigation-compose` 2.8.5). `ui/navigation/KataNavHost.kt` — one flat `NavHost` (no nested graphs), 2 destinations: `Routes.CART` ("cart") and `Routes.SUMMARY` (string route `"summary?code={code}&pct={pct}&category={category}"` in `ui/navigation/Routes.kt`, built via manual `Uri.encode` string concatenation). Routes are plain `String` constants — NOT type-safe (`@Serializable` or `NavKey`). No nested navigation, no shared/multi back-stack destinations, no deep links. CartScreen uses default-param `viewModel(factory = CartViewModel.Factory)`; SummaryScreen's VM is built inline in `KataNavHost` from `backStackEntry.arguments` via `SummaryViewModel.factory(code, pct, category)` — per-screen ViewModel wiring, no shared ViewModel across destinations.

Gap vs. Nav3 migration guide prerequisites: **compileSdk 35 → needs 36+ (GAP, blocking)**; minSdk 24 already ≥ 23 (OK). Routes are plain strings, not `NavKey`-implementing types (GAP — must convert to type-safe `NavKey` data classes/objects as part of the atomic cut-over). Guide's unsupported-feature list (nested nav beyond one level, shared destinations across back stacks, custom destination types, deep links) — **NONE of these apply here**: flat, 2-destination, single-back-stack, no-deep-link app — a favorable/low-risk Nav3 migration candidate once compileSdk is bumped and routes become `NavKey` types. Risk: AGP 8.6.1's support ceiling for compileSdk 36 is unconfirmed — may require an AGP bump too (needs `sdd-research` verification before `sdd-propose`).
Severity: Medium. Effort: Small-Medium (only 2 screens to convert).

### Goal 2 — Behavioural testing
Current suite (`app/src/test/java/com/pedidosya/kata/**`, JUnit4 + MockK + kotlinx-coroutines-test + Turbine, no Robolectric): `CartMapperTest`, `CouponMapperTest`, `CartRepositoryImplTest`, `CouponRepositoryImplTest`, `AppContainerTest`, `CalculateTotalsTest`, `ValidateCouponTest`, `CartViewModelTest` (14 tests), `SummaryViewModelTest`. `CartViewModelTest` is genuinely behavior-focused: asserts on public `state`/`events` Flows via Turbine `.test{}`, not internals — good pattern to keep. `androidTest` has exactly one file, the AGP-scaffolded `ExampleInstrumentedTest`, which asserts `appContext.packageName == "com.pedidosya.kata.fruit_store"` — **stale/wrong package assertion** (real applicationId is `com.pedidosya.kata`); would fail if ever run — concrete bug, currently dead weight.
Gaps: zero Compose UI tests exist anywhere (despite `androidx.compose.ui:ui-test-junit4` already declared as `androidTestImplementation` — unused dependency); zero coverage of `CartScreen`/`SummaryScreen` composable branches (Loading/Error/Success rendering, button enablement, `PullToRefreshBox` trigger, coupon status message text); zero navigation-level test; zero screenshot tests despite 100%-Compose UI; zero end-to-end/user-journey test spanning Cart→Apply→Confirm→Summary. `MainDispatcherRule` defaults to `UnconfinedTestDispatcher`, and every `CartViewModelTest` test explicitly re-passes `runTest(UnconfinedTestDispatcher())` — per official coroutines-test guidance, Unconfined can hide ordering bugs vs. `StandardTestDispatcher` + explicit `advanceUntilIdle()`.
Severity: Medium-High (UI behavior is completely unverified). Effort: Medium.

### Goal 3 — Compose stability/recomposition audit
Positive baseline: every domain/UI-state type is `val`-only (`CartItem`, `Coupon`, `CartTotals`, `CouponValidationResult`, `CartUiState`, `SummaryUiState`, `CartEvent` — confirmed via direct read, zero `var` properties found). Zero `@Immutable`/`@Stable` annotations exist anywhere (grep-confirmed). Both screens correctly use `collectAsStateWithLifecycle()` (not raw `collectAsState`) — matches official guidance, no gap.
Concrete stability gap: `CartUiState.Success.items: List<CartItem>` and `SummaryUiState.Success.items: List<CartItem>` are raw `kotlin.collections.List` — per the official Stability doc, plain `List`/`Set`/`Map` are treated unstable by the Compose compiler by default, which makes the *containing* `Success` data class unstable overall. This makes `CartContent`, `CouponSection`, `SummaryContent` non-skippable — they recompose on every parent recomposition regardless of whether the data actually changed. Fix path: `@Immutable` on `CartUiState.Success`/`SummaryUiState.Success` or migrate `items` to `kotlinx.collections.immutable.ImmutableList`.
No compiler stability/metrics report is wired up (no `compose_metrics`/`compose_reports` compiler args) — this audit is a manual code read only; a `classes.txt`/`composables.txt` report must be generated in a later phase to confirm strong-skipping-mode behavior and get an authoritative unstable-class list.
Severity: Medium. Effort: Small.

### Goal 4 — ViewModel UI state definition
Both ViewModels use a single closed sealed-interface `UiState` pattern (`CartUiState`: `Loading`/`Error`/`Success` with computed `canConfirm`; `SummaryUiState`: `Loading`/`Success`) — consistent shape across both, matches official state-holder guidance.
Inconsistency found: `SummaryViewModel.state` uses `repository.observeCart().map{}.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), Loading)` — matches the design doc's originally-planned pattern. `CartViewModel.state`, however, does NOT use `stateIn` at all — it hand-rolls a `MutableStateFlow<CartUiState>` (`_state`) mutated imperatively from many call sites. This **diverges from `sdd/shopping-cart/design`'s own documented data-flow** (`combine(observeCart(), couponState, refreshState){...}.stateIn(...)`), which was never implemented as designed — a real design/code drift worth reconciling before/during this modernization.
One-shot events: `CartViewModel` exposes `_events = MutableSharedFlow<CartEvent>(extraBufferCapacity = 1)` (replay = 0) for `NavigateToSummary`, collected via `LaunchedEffect(viewModel) { events.collect{} }` in `CartScreen`. Per the kotlin-concurrency-and-flow skill, a one-consumer navigation handoff that must survive a collector gap should use a buffered `Channel` + `receiveAsFlow()`, not a replay-zero `SharedFlow`.
Severity: Medium. Effort: Small-Medium.

### Goal 5 — Structured concurrency with coroutines
Grep-confirmed zero occurrences of `GlobalScope`, `runBlocking`, custom `CoroutineScope(...)`, or `CoroutineExceptionHandler` anywhere in `app/src/main`. Both ViewModels use only `viewModelScope.launch{}` — correct auto-cancellation ownership. `CartRepositoryImpl`/`CouponRepositoryImpl` both inject `CoroutineDispatcher = Dispatchers.IO` via constructor default (testable); `withContext(dispatcher)` wraps all I/O; `runCatching{}` at the repository boundary converts failures into `Result`/`CouponValidationResult.ServiceError` before they reach ViewModel-owned coroutines. `AppContainer` does not inject a dispatcher when constructing repositories (relies on the `Dispatchers.IO` default) — no shared `DispatcherProvider` abstraction exists; acceptable at current scale. Single `LaunchedEffect(viewModel){ events.collect{} }` usage in `CartScreen` is correctly keyed and composition-scoped; no off-screen-composition risk exists (only 2 linear screens, no pager). Room `CartItemDao` is clean: `Flow`-returning query, `suspend` mutations, transactional `replaceAll`.
Severity: Low-Medium (already largely compliant). Effort: Small.

### Recommendation on SDD change granularity
Recommend **splitting `architecture-modernization` into multiple sequenced SDD changes** rather than one proposal covering all 5 concerns: the goals have different risk profiles, touch different layers, and have a real dependency. Nav3 migration (goal 1) requires a compileSdk/AGP bump that is itself a build-wide risk surface separate from ViewModel/Compose-layer concerns (goals 3-5); behavioral testing (goal 2) should land AFTER the ViewModel-state/concurrency reconciliation (goals 4-5) so new UI tests are written against the final state-production shape. A single proposal spanning build-system, navigation, 2 ViewModels, and new test infra would also blow the 400-line PR review budget by a wide margin (shopping-cart was already ~1500-1900 lines/High risk for one feature).

Suggested split and dependency order:
1. `viewmodel-state-and-concurrency` (goals 4+5 combined — same layer, same files: `CartViewModel`/`SummaryViewModel`/events). No external dependency; foundational, do first.
2. `compose-stability-audit` (goal 3) — depends on (1) landing first so `@Immutable`/`ImmutableList` annotations apply to the already-settled state shape.
3. `behavioral-testing-expansion` (goal 2) — depends on (1) and (2) so new Compose UI tests assert against final state shapes and stable composables; also fixes/removes the broken `ExampleInstrumentedTest`.
4. `navigation-3-migration` (goal 1) — independent of 1-3 in principle, sequenced last because it carries the only build-wide infra risk (compileSdk/AGP bump needs `sdd-research` first).
